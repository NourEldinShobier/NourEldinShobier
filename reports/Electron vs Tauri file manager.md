# Electron beats Tauri for VSCode-class file managers

**Recommendation: choose Electron for this project, with moderate confidence.** A heavy, extensible, VSCode-like file manager that may later host a code editor, terminal, video player and PDF viewer sits in the area where Tauri's tradeoffs hurt most. Tauri gives you one consistent advantage, a much smaller installer (macOS: **57 MB vs 323 MB** in the one controlled comparison found), plus a Rust core that suits heavy file work. Electron gives you the things this project depends on: a single bundled Chromium, built-in native drag-out of files, a built-in file-icon API, and a Node `utilityProcess` that works as a VSCode-style extension host. Tauri's RAM and startup advantages are weaker than its marketing suggests, and on Windows it runs Chromium anyway. Read this as a decision-grade judgment on partial evidence. The official Electron and Tauri docs sites, GitHub's API and npm were blocked during research, so much of the Electron side, and several decisive Tauri facts, are unverified background knowledge. The report marks which claims are which. Before committing, run a one- to two-week spike on the three riskiest items: Linux video and scrolling in Tauri's webview, file drag-out, and the extension-host design.

## What was verified and what was not

Evidence quality is uneven, and the imbalance favors Tauri's weaknesses being documented and Electron's strengths being assumed. The best-sourced material came from Tauri and Electron docs mirrored on GitHub (drag-and-drop, `utilityProcess`, the `app` API, the Tauri sidecar and updater pages), from WebKit bug-tracker entries, and from Tauri GitHub issues and discussions. The weakest areas are the following. Electron's codec set, its built-in PDF viewer, `node-pty`, and Monaco/CodeMirror behavior were not sourced at all. No reproducible 2025-26 benchmark of Tauri 2.x against Electron 3x/4x exists in the notes, and CPU and battery comparisons were not found. Star counts, npm download counts, production-app lists, security models, and Tauri's tray, shortcut, menu, notification and deep-link plugins were not checked. Alternatives such as Wails, Electrobun, Qt and native toolkits were not researched. Where this report states something as background, it says so. The recommendation rests mainly on the sourced Tauri gaps below, which stand on their own, rather than on the unverified Electron strengths.

## Electron's built-in features cover the gaps that matter to a file manager

The sharpest sourced gap is native drag-out of files to the desktop or other apps. Electron supports it directly: the renderer prevents default on `ondragstart`, sends IPC, and the main process calls `webContents.startDrag({file, icon})` ([Electron docs](https://github.com/electron/electron/blob/main/docs/tutorial/native-file-drag-drop.md)). Tauri supports dropping files into the window but not out. The core issue requesting drag-out, opened by someone building a file manager, was **closed as "not planned"** ([tauri #6664](https://github.com/tauri-apps/tauri/issues/6664)). The workaround is CrabNebula's `tauri-plugin-drag`, which covers macOS, Windows and Linux, and its README says it was tested with Tauri v2. On Linux, though, the Rust API needs a `gtk::ApplicationWindow`, and the repository showed 16 open issues that were not read ([drag-rs](https://github.com/crabnebula-dev/drag-rs)). It is usable, but it is a third-party dependency on a feature that is central to a file manager, and its Wayland behavior is unverified.

Two smaller sourced gaps follow the same pattern. Electron's `app.getFileIcon(path)` returns the OS icon for a file ([Electron app API](https://github.com/electron/electron/blob/main/docs/api/app.md)), which a file manager needs for every row; the notes found no official Tauri equivalent, so per-OS icon and thumbnail code would be custom Rust. Tauri's official clipboard plugin documents only text ([tauri-docs](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/clipboard.mdx)), whereas a file manager needs file-list copy and paste. Whether community plugins fill this was not checked, and neither was Electron's file-clipboard behavior. Single-instance locking and protocol handlers are both documented for Electron (`requestSingleInstanceLock`, `setAsDefaultProtocolClient`); the equivalent Tauri plugins could not be verified because the docs were blocked, so that comparison is open rather than a Tauri deficit.

Tooling and distribution also lean Electron. Tauri's WebDriver tooling does not cover macOS, and the request for it (tauri #7068) is open and marked help wanted; the alternatives are an embedded WebdriverIO provider or a CrabNebula provider that needs a paid API key ([tauri #7068](https://github.com/tauri-apps/tauri/issues/7068), [WebdriverIO](https://webdriver.io/docs/desktop-testing/tauri/platform-support)). Tauri's updater requires its own signing scheme, cannot disable it, and on Windows the app must quit before install ([updater docs](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/updater.mdx)). Tauri's distribution page lists Flatpak and others, but a Flatpak bundling request opened in 2022 still looks open, and one developer reported no native MSIX support ([tauri #3619](https://github.com/tauri-apps/tauri/issues/3619), single-source). Playwright's Electron support and Electron's updater and builder matrix are background knowledge, not verified here.

## A VSCode-style extension host is natural in Electron and custom work in Tauri

Extensibility is the requirement that most separates the two. Electron's `utilityProcess.fork` creates a Node.js child with message ports, and the main process can transfer `MessagePortMain` objects to it ([Electron docs](https://github.com/electron/electron/blob/main/docs/api/utility-process.md)). That is the basic ingredient of VSCode's model: a separate Node extension-host process with webview-based UI contributions. The VSCode architecture itself was not sourced in the notes. The downside, also unsourced, is that extensions get full Node power unless you sandbox them, and the utilityProcess docs say nothing about sandboxing the child.

Tauri plugins, by contrast, are Cargo crates compiled into the app, optionally with an NPM API package ([Tauri plugin docs](https://v2.tauri.app/develop/plugins/)). They are first-party extension points, not a way for third parties to add features at runtime. The realistic options for a runtime extension system are a Node or Deno sidecar, which must be shipped per target triple and adds back binary size ([sidecar docs](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/develop/sidecar.mdx)), or WASM. Spacedrive, a Tauri-based file manager with a Rust core, has built a WASM extension system with manifest-declared permissions. It is early: AI inference, tags and custom fields return `NotAvailable`, and some declarable permissions have no host implementation ([Spacedrive README](https://raw.githubusercontent.com/spacedriveapp/spacedrive/main/extensions/README.md)). The notes found no Tauri project running a VSCode-style JS extension API, and no official Tauri guidance for Extism or Wasmtime ([Extism](https://docs.rs/crate/extism)). My inference is that WASM suits data and job extensions such as thumbnailers and indexers, but UI-heavy extensions like an editor or video player would need a separate mechanism such as iframes or per-extension webviews. Tauri's multiwebview support is still behind the `unstable` Cargo feature ([tauri Cargo.toml](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/Cargo.toml)), so pane layouts built on it carry API-stability risk.

## Media and editor extensions are where system webviews hurt most

Chromium everywhere means a future video extension behaves the same on all three operating systems. Tauri's webviews do not offer that. On Linux, WebKitGTK video depends on installed GStreamer plugins, and missing sets cause H.264 and AAC failures ([WebKit bug 245850](https://bugs.webkit.org/show_bug.cgi?id=245850)). HLS was disabled in WebKitGTK 2.39.4 ([WebKit bug 255495](https://onbugs.webkit.org/show_bug.cgi?id=255495)), and a Tauri app using hls.js failed on Linux with a missing-AAC-plugin warning while working on Windows and Android ([Manjaro forum](https://forum.manjaro.org/t/webkit2gtk-doesnt-work-well-with-m3u8-streams/168103), anecdote). A Tauri maintainers' discussion, with comments through August 2026, shows one user still seeing WebKitGTK MP4 streams stop short of the end even with buffer headers; the proposed workaround, libmpv in a child window repositioned to track an HTML div, is not true embedding, and native windows draw above the webview ([tauri discussion 6343](https://github.com/orgs/tauri-apps/discussions/6343)). The plugin for it, `tauri-plugin-libmpv-api`, was last updated in November 2025 with a low maintenance score, and macOS and Linux need a system libmpv ([package listing](https://classic.yarnpkg.com/en/package/tauri-plugin-libmpv-api)). A robust Tauri video story therefore needs tiers: native `<video>` where the platform allows it, ffmpeg transcode behind a range-capable protocol, and libmpv for power users. On Windows, HEVC needs Microsoft's paid or OEM extension regardless of framework. Electron's exact codec set (background knowledge says official builds include H.264 and AAC, with HEVC, AC3 and MKV varying) was not verified, so the media advantage is confirmed on the Tauri-weakness side only. Electron also has the overlay problem if you want libmpv, so native-quality playback is hard in both.

Rendering on Linux is a second risk. Tauri's own Linux graphics page documents blank windows and flicker on NVIDIA/WebKitGTK mismatches, and warns that WebGL2 may silently run in software with a masked renderer string, causing low frame rates in terminals, editors and charts ([Tauri Linux Graphics](https://v2.tauri.app/develop/debug/linux-graphics/), via search summary; tracked in tauri#9394). The workarounds disable DMABUF or accelerated compositing, which costs speed. WebKit also has a long-running GTK slow-scrolling bug ([WebKit 221738](https://bugs.webkit.org/show_bug.cgi?id=221738)). A VSCode-like app puts a terminal (xterm.js), a Monaco or CodeMirror editor and long virtualized lists on screen at once, so it is the profile most exposed to these problems. Whether Monaco and CodeMirror 6 behave across all three webviews was not sourced; my background expectation is that they generally work, with CodeMirror 6 lighter, but you should test on the oldest WebKitGTK you intend to support.

For the terminal, the Tauri pattern is xterm.js plus a Rust `portable-pty` backend over Tauri events. The reference project is a proof of concept last updated in November 2023 ([write-up](https://prompts.brightcoding.dev/blog/marc2332tauri-terminal-build-a-terminal-emulator-in-tauri)), and `tauri-plugin-pty`, created in January 2026, is described as in development ([docs.rs](https://docs.rs/tauri-plugin-pty)). So you would own a small Rust wrapper. Electron's `node-pty` route is the established one by background knowledge, but needs native-module rebuilds per Electron version; neither claim was sourced. PDF is a closer call. Tauri can use pdf.js or native PDFium via `pdfium-render`, which needs you to bundle the PDFium binary and is not thread-safe ([docs.rs](https://docs.rs/crate/pdfium-render)); one project measured Rust/PDFium 2 to 6 times faster than pdf.js on heavy documents, with about 3 ms vs 60 ms IPC overhead on near-empty pages ([project notes](https://gitcode.com/gh_mirrors/op/open-pdf-studio/tree/main/mcp-server), anecdotal). Electron's built-in Chromium PDF viewer is background knowledge only.

## Tauri's performance edge is real in size and Rust compute, but not in RAM or startup

Installer size is the one consistent Tauri win. Better Stack built the same screen-recorder app in four frameworks and found macOS bundles of **57 MB for Tauri vs 323 MB for Electron**, but idle memory of only **109 MB vs 128 MB**, and startup of **311 ms for Tauri vs 273 ms for Electron** ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/), via search summary; versions not retrieved). Other sources claim far larger gaps, such as 42 MB vs 168 MB idle and 380 ms vs 1,420 ms cold start, but without verifiable methods ([tech-insider](https://tech-insider.org/tauri-vs-electron-2026/)), so treat them as marketing-grade. The memory picture is subtler than the headline. A Tauri maintainer-era issue re-measured with shared memory counted properly and found default hello-world apps nearly equal (Electron 118 MB USS vs Tauri 125 MB on Ubuntu), and real web apps larger under Tauri's WebKit on macOS and Linux: vscode.dev used about 429 / 572 / 370 MB in Tauri vs 332 / 222 / 312 MB in Electron on macOS / Ubuntu / Windows ([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889), 2022 data and old). On Windows, Tauri uses WebView2, which is Chromium, so memory is near parity. For a heavy, VSCode-like UI that will be loaded with editor and terminal content, expect RAM roughly equal, not a Tauri win. Measurement artifacts cut both ways, because macOS WebKit helper processes may not be attributed to the app.

IPC is a weak spot for Tauri that matters here. Tauri 2 added a serialization-free binary response type, but it still rides the webview's fetch-like path. An informal test reported a 10 MB binary payload at about 5 ms on macOS and about **200 ms on Windows**, and a maintainer said it is unlikely to improve much with system webviews ([discussion 11915](https://github.com/orgs/tauri-apps/discussions/11915), non-scientific). No Electron IPC benchmark was found, so this is not a measured Electron win; Chromium's cross-process buffer transfer is copy-based as well, per old background material. The practical advice holds for both: stream and paginate large directory listings and thumbnail data, and in Tauri prefer the asset protocol for images instead of invoke.

Rust's real strengths are in backend work: parallel recursive traversal, search, hashing, long-lived indexes and memory control for millions of entries. A Rust napi addon self-reported about 12x faster recursive readdir than Node on a roughly 30,000-entry tree ([rush-fs](https://github.com/CoderSerio/hyper-fs/pull/1), author's benchmark), but a flat single directory is syscall-bound, and parallel walking helps deep trees, not wide directories ([jwalk](https://codegraph.jelmer.uk/rust-jwalk/0.8.1-1/README.md)). The same addon route means Electron can capture most of the benefit with napi-rs, at the cost of per-platform native packaging. So Tauri's advantage here is ergonomic (the Rust crate is called in-process) more than a hard ceiling. No head-to-head file-manager benchmark exists in the notes. Spacedrive, the leading Tauri-plus-Rust file manager, added index caching and filesystem watching in late 2025 but had paused development for funding reasons in early 2025 ([AlternativeTo](https://alternativeto.net/news/2025/3/spacedrive-pauses-development-due-to-funding-challenges)). That is not strong evidence for or against the stack, and no postmortem was found.

## Ecosystem and maturity favor Electron, but Tauri is stable and moving

Tauri 2.0 shipped on 2024-10-02, about a month after its planned release candidate window ([Tauri changelog](https://v2.tauri.app/release/tauri/)), and a Tauri 3 alpha line exists. The `tauri` crate showed about **35.0M total and 13.6M 90-day downloads** with max version 3.0.0-alpha.4 ([crates.io](https://crates.io/api/v1/crates/tauri)). Those figures include CI and transitive pulls and cannot be compared with npm's `electron` numbers, which were not obtained. Governance is a Programme within the Dutch Commons Conservancy, with CrabNebula as the commercial partner ([Tauri governance](https://v2.tauri.app/de/about/governance/), [Tauri blog](https://v2.tauri.app/blog/3/)); the same company maintains the drag plugin and a paid test provider, which concentrates single-vendor risk, though that risk was not quantified. Electron ships a major every 8 weeks and supports only the latest three majors ([Electron timelines](https://electronjs.org/de/docs/latest/tutorial/electron-timelines)), which implies an upgrade roughly every six months to stay supported. Electron 40 reached Chromium M144 in January 2026 and Electron 43 was in beta with Chromium 150 in June 2026 ([Electron releases](https://releases.electronjs.org/)). That treadmill is a real cost, but it also means Chromium security fixes arrive within weeks.

A possible game changer is Tauri's CEF work. Fragments in the notes (a March 2026 task and a May 2026 v3 alpha fix) suggest a Chromium Embedded Framework runtime in the v3 alpha ([digest](https://buttondown.com/thewang/archive/rust-daily-digest-2026-05-24/)), and the March task notes missing basics like back and forward in the public API ([task](https://hub.harborframework.com/tasks/abundant/tauri-apps__tauri-14661)). No official doc was found, so its status is unconfirmed. If it matures it would remove Tauri's webview inconsistency at the cost of its size advantage, which weakens the case for choosing Tauri's current model while eroding what differentiates it. It is worth monitoring, not betting on. Public migrations exist in both directions of sentiment: Vikunja, Aptabase and others moved to Tauri citing size, memory and free OS webview security updates ([Aptabase](https://aptabase.com/blog/why-chose-to-build-on-tauri-instead-electron)), while commenters say the cost of testing across multiple runtimes is why most developers stay on Electron ([DEV comments](https://dev.to/best_codes/why-i-ditched-electron-for-tauri-588k/comments)). Electron remains the engine behind VS Code, Slack and Claude Desktop per a blog audit ([codenote.net](https://codenote.net/en/posts/famous-electron-apps-2026-research/)); Teams moved to WebView2 and Zed built a native app. Zed's choice points to the third option, not covered by the research, of skipping web UI frameworks entirely.

## Is Tauri worth choosing, and what would change the answer

For this project, no, unless one of four conditions holds. Tauri becomes the better choice if the product's core value is a small, fast, Rust-native file engine (indexing, search, dedupe) with a modest UI, if you can accept Windows- and macOS-first support with Linux best-effort, if extensions will be data-oriented WASM modules rather than UI contributions, and if the team already writes Rust. Tauri also becomes more attractive if the CEF runtime proves production-ready, since it would give a uniform engine. If the plan really is a VSCode-like platform where third parties ship editors, viewers and players, Electron wins on the points that hurt most to retrofit: the extension host, codec uniformity, drag-out, file icons, and testing across three operating systems.

A pragmatic path hedges the main risk. Keep the file-heavy logic (traversal, watching, hashing, thumbnails) in a separate Rust or native module with a clean interface, load it into Electron through napi-rs or a utility process, and treat Tauri as a later option for a lighter edition. Whichever you choose, avoid sending large listings as JSON, run heavy work off the UI thread, and test early on the oldest supported Linux distribution.

## Conclusion

The research changes the question from "which is faster" to "which consistency guarantees do you need". Tauri's headline RAM and startup advantages shrink under careful measurement and vanish on Windows, leaving installer size and a Rust backend as its durable strengths. Electron's advantages are structural: one engine, built-in native affordances for file managers, and a process model that fits extension hosting. Both camps' best arguments are thin on independent benchmarks, so the largest remaining uncertainties are empirical ones you can test cheaply. Measure idle and loaded memory with your own UI on all three operating systems, run your target video files through Linux WebKitGTK, and prototype a minimal extension host in each stack before committing.
